# 换向后重新跟随并落台：专项场景

上一轮 session004 已证明四种二维运动落台及一次换向安全退出，但没有实际触发 `PLANAR_REACQUIRE`。本次增加独立分支覆盖试验，目标是实际记录：下降中的平台换向 → 停止下降并重新跟随 → 再次规划下降 → 真正落台。当前代码与数值检查不替代这条流程的物理验收。

## 为什么使用独立高净空场景

原场景在约1.5米脚底净空完成跟随，重新跟随门控还必须预留停止下降距离、1.25米保护底线和0.25米余量，因此突变后可能已经没有足够空间重接。专项配置将对齐参考净空设为4米，在实测开始下降且脚底净空处于3.4—3.85米时触发一次平台反向。实际工作进程参数下的规划轨迹检查发现2.5米仍可能在平台限幅响应期间失去重接余量，因此没有使用该较低试验高度。新下降候选为6、8、10秒。该变化属于独立试验初始条件，不是与旧场景相同初态的性能对比，也没有降低任何接触、飞行或退出门限。

三个场景分别在X、Y、XY方向反向。运动指令继续经过原合成速度、加速度、jerk限幅与物理关节力控制。触发器读取实际净空、竖直速度和当前执行阶段；不把目标速度、触发条件或未来命令送进滤波器、规划器或着陆决策。每次尝试只触发一次，重新跟随过程中不重复切换目标。

## Ubuntu 运行

进入更新后的仓库 `毕设仿真/`，使用新的、不存在的 session 目录：

```bash
python3 tools/run_planar_simulation.py \
  --profile planar_reacquisition_v1 \
  --base /home/haosheng/hs_ardupilot_stage1 \
  --session /home/haosheng/hs_ardupilot_stage1/interactive_20261023/reacquisition_session_001
```

沿用当前已验证的 Ubuntu 容器/桌面启动环境，保留其 DISPLAY、XAUTHORITY、XDG_RUNTIME_DIR 和 DBus 设置。源资产目录不同则使用已有的 `--source` 和 `--frozen` 参数。不要与使用相同飞控端口的另一场仿真重叠启动。原始世界5米和已归档3米的平台初始位置均被明确识别，其他位置会拒绝，不静默覆盖未知场景。

默认 profile 仍为原五场 `planar_landing_v1`；专项试验必须显式选择新 profile。脚底净空更高可能改变运行时间，原40秒总任务、25秒累计等待和3次重新跟随预算保持。

## 严格验收

每场结束后执行：

```bash
python3 tools/audit_planar_reacquisition.py RUN_DIRECTORY
```

此命令重新运行因果策略/经验余量审计、原生 LAND/非强制停转审计、真正落台时的原接触和支撑审计、原始飞机 COM 运动审计及平台原始物理位姿审计，并额外要求：

- 触发记录与同一控制时刻的实测净空、下降速度、TRACKING阶段相符。
- 触发后存在真正的 `PLANAR_REACQUIRE` 控制记录，而非只改状态文本。
- 此后出现新的 `ALIGNMENT_COMPLETE` 和 `PLAN_ACTIVATED`，均早于实际物理接触。
- 平台原始位姿差分显示受测轴从正向变成负向，负向证据至少连续四个速度间隔，不能仅靠场景名称或指令判断。
- 全部原物理、正常停转、停转后支撑和飞机速度/加速度门限通过，预算不超限。

安全退出、未触发换向、未重新跟随、只有对齐没有新规划，都不会被计为专项成功。保留这些失败记录，不放宽门限来凑通过。平台原始响应仍从实际位姿测量，不把指令0.12m/s²或0.3m/s³当成实际响应保证。

验收可重复运行。原生 LAND 和接触审计要求输出不存在，因此专项脚本会临时归档已有报告，独立重算、比较，再恢复原报告字节；新计算和日志留在 `results/reacquisition_audit_replays/`。重算失败或结果不同均拒绝通过。只对已结束且未解锁的试验运行验收，不并发对同一试验启动多个审计。

结果至少保存 `scene_maneuvers.json`、完整 `receding_control.jsonl`、规划请求/响应、`receding_session.json`或尝试记录、原始 Gazebo 位姿、DataFlash、原始/生成模型及各项审计。完整日志留 Ubuntu，GitHub只同步必要轻量结果和运行配置。新配置在取得这些物理证据前保持“待验证”。
