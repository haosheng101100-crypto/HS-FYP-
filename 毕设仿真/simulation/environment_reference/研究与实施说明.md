# 从官方 Gazebo 场景到车机协同

项目基于 [ArduPilot/ardupilot_gazebo](https://github.com/ArduPilot/ardupilot_gazebo)，实际运行在 Ubuntu 虚拟机的 Gazebo Harmonic 中。“仿真界面”指 Gazebo 的原生图形界面。

## 仓库提供了什么

这个仓库提供仿真连接插件、示例模型和场景。车机协同控制逻辑需要接在它提供的仿真基础上。

| 官方代码 | 在本项目中的作用 |
|---|---|
| `worlds/iris_runway.sdf` | 跑道、地形、光照、地理坐标和传感器系统；我们的世界直接从它生成 |
| `models/iris_with_gimbal/model.sdf` | 四旋翼控制插件、旋翼升力/阻力、云台；保留这些动力学配置 |
| `models/iris_with_standoffs/model.sdf` | 机体、起落架、旋翼、质量和惯量、IMU |
| `src/ArduPilotPlugin.cc` | Gazebo 与 ArduCopter SITL 的 JSON 数据交换，以及旋翼控制输出 |
| `config/gazebo-iris-gimbal.parm` | 与官方 Iris 云台和输出通道相匹配的参数 |

已获取的上游版本为 `082a0fe231f6e63bc8d1598f1cba461d9e2ea7f5`。上游目录的 Git 工作区没有修改；新增代码、车辆和场景保存在项目自己的目录中。`results/source_snapshot.json` 保存了版本和原始文件哈希。

## 第一阶段如何接进来

`first_stage/core.py` 和 `first_stage/integration.py` 从已有第一阶段项目复制。原有的位置历史、短时运动预测、PID、速度前馈以及 TRACK / DESCEND / HOLD / LANDED 状态机继续使用。

```mermaid
flowchart LR
  G[Gazebo 实际位置与车顶接触] --> P[第一阶段历史与运动预测]
  P --> C[PID 跟踪与降落状态机]
  C --> M[MAVLink 速度和朝向目标]
  M --> A[ArduCopter 飞控]
  A --> J[官方 ArduPilotPlugin]
  J --> G
  V[车辆速度指令] --> D[Gazebo DiffDrive 驱动车轮]
  D --> G
```

新接口位于 `tools/cooperation_demo.py`。Gazebo 提供真实模型运动，ArduCopter 承担无人机姿态与电机控制。第一阶段控制器承担车机相对运动和任务状态转换。

原来的 `cooperation_demo.py` 使用水平位置 PID 输出速度目标，竖直速度由高度误差比例项和下降参考高度给出。这个入口起飞调用飞控 TAKEOFF 指令，姿态由飞控控制。倾斜和朝向检查本身不属于自主姿态控制。

新增的 `attitude_demo.py` 使用自己的速度 PI 计算期望加速度、倾斜目标和总推力，再由 `control/attitude_pid.py` 中的三轴姿态角 PID 根据反馈计算机体系角速度。通过 `SET_ATTITUDE_TARGET` 掩码 128 与纯推力模式发送，保留飞控的角速度内环、电机混控和倾斜推力补偿。这个入口起飞不调用 TAKEOFF，车顶接触后的电机停转交给标准 LAND 模式。

当前先用 Gazebo 真值作为观测，连接完整闭环。尚未加入视觉识别、观测噪声、通信延迟、风和道路颠簸，因此这些结果只说明当前仿真条件下的流程可以运行。

## 坐标、时间与姿态

- 控制器使用世界 ENU：x 东、y 北、z 上。官方插件对应的飞控 NED 速度为 `(vy, vx, -vz)`。速度指令不依赖两个坐标系原点相同。
- 模型位姿向量的时间戳在每个 `pose.header.stamp` 内。算法步进依据仿真时间；连接超时和消息过期依据实际经过的时间。
- 车顶目标是车辆原点向上 0.80 m。无人机参考点是机体原点向下 0.195 m 的起落架最低点。参考点偏移经四元数旋转后进入世界坐标，避免把机体原点误当成接地点。
- 无人机朝向目标由车辆直行朝向给出。允许下降前还检查无人机倾斜与相对朝向。姿态是下降条件之一，协同跟踪仍然围绕相对位置和速度展开。
- 车辆目前只做平地低速直行。没有增加车辆姿态控制课题。
- 降落完成需要车顶接触反馈和相对运动条件；最终使用正常 LAND 模式停转，没有强制解除解锁。

## 新增模型与场景

`models/landing_vehicle/model.sdf` 是轮式车辆，有两个驱动轮、前后支撑、车身和带碰撞结构的 2.0×1.4 m 平台。Gazebo DiffDrive 插件通过轮关节驱动，不直接修改车辆位置。

`models/stage1_iris/model.sdf` 由官方 `iris_with_gimbal` 复制，仅增加模型位姿发布。`worlds/uav_vehicle_stage1.sdf` 由官方跑道世界复制，仅替换为带位姿输出的 Iris 包装模型，并增加车辆和接触系统。

观察相机安装在车辆传感器配置中，随车辆移动，记录真实 Gazebo 渲染画面。它没有额外质量或碰撞体。

## 环境处理

原虚拟机是 Gazebo Classic 11 与 ROS 2 Humble。官方仓库推荐的现代 Gazebo 与旧环境存在命令包冲突，因此 Harmonic 的 OSRF 包被解压在 `gz_prefix` 中，启动时显式配置库、插件、QML 和资源路径。Ubuntu 基础依赖通过 `apt --no-remove` 安装。

虚拟机 GPU 在 OGRE2 下出现着色器错误。使用 [Gazebo 官方排障建议](https://gazebosim.org/docs/harmonic/troubleshooting/)中的软件渲染方式，仍运行 Harmonic 和官方原始模型。启动脚本先等待 Gazebo 时钟与 IMU 初始化，再启动飞控；飞控早期退出时记录退出状态，并最多重试三次。

## 依据与后续顺序

接口依据 [官方仓库 README](https://github.com/ArduPilot/ardupilot_gazebo#usage)、[Guided 控制指令文档](https://ardupilot.org/dev/docs/copter-commands-in-guided-mode.html) 和 [Gazebo DiffDrive 接口](https://gazebosim.org/api/sim/8/classgz_1_1sim_1_1systems_1_1DiffDrive.html)。上游模型与代码保留原许可。

实施顺序为：官方场景加载 → 加入车辆和平台 → 接入第一阶段控制器 → 静止车顶降落 → 低速跟车后停车降落 → 运动中车顶降落。之后再根据毕业设计要求逐项加入变速、转弯、延迟和误差。

2026-10-14 已取回静止降落、跟车后停车降落及运动中降落三种流程的完成记录，并重新现场演示了跟车后停车降落，保存为 `results/follow_20261014_cooperation_status.json`。这些旧流程使用 ArduCopter 自带姿态控制器。

同日按用户明确的要求接入自己的姿态角 PID，实际完成起飞、悬停、20° 偏航跟踪、跟车与车顶降落。结果为 `results/attitude_demo_status.json`，`completed: true`；实际角度、指令和 P/I/D 分量保存在对应 CSV，录像与响应图也已保存。实体机适配尚未完成，增益与推力基准属于当前仿真模型。完整控制关系见 [姿态 PID 与起降原理](姿态PID与起降原理.md)。
